## 1. 目的

`/nfgo` のワークフローを改訂し、単一 Issue 内のタスク分解を早めに行い、独立した委譲を並列に実行できるようにする。before 実測 (`/nfgo 18`、2026-11-25) では壁時間 23 分 25 秒のうち architect 子が 12 分 44 秒 (入力 226k トークン — 調査報告の全文転載が原因) を占め、クリティカルパスの過半が設計委譲だった。並列委譲の実効性は実機検証済み (調査 2 件の重複 92.975 秒、逐次相当 429 秒 → クリティカルパス 336 秒)。

原則 (Issue #49): Delegate early / Parallel by default / Minimize the critical path / Avoid duplicate work / Sequential only when necessary。

## 2. 事実と現状の制約

### 2.1 事実 (OpenCode v2.4.x 標準機能、調査報告 0001/0002)

1. primary は 1 ターンで複数 subagent を起動でき、子は独立バックグラウンドジョブとして並行実行される (P1: 2 子の busy 区間重複 531 ms)。並列数の公式上限は確認できていない (不在の確認)。
2. 子からの再委譲は `experimental.subagent_depth` (既定 1) の引き上げが必要。experimental は予告なく変更されうる。depth と permission は独立機構。
3. 子は自分に設定された権限・モデルで動く (親権限のサブセットではない)。
4. 子の報告は `<background-result>` として idle ごとに届く。state=`running` は中間報告であり、完了と誤認してはならない。親に転送されるのは子の**最後の text 応答のみ**。
5. 計測はセッション DB (`session_v2`: parent_id, time_busy/idle, tokens) または公式 API (`session.list?parentID=`, experimental job API) で機械可読。

### 2.2 現状の制約 (ローカル調査)

- 5 役すべての agent 定義本文が子エージェント起動を禁止。implementer は `subagent` を明示 deny、他 4 役は deny-all (`{"*", "*"}`) により実質不可。
- `.opencode/commands/nfgo.md` L27 が複数 Issue 間の並列を禁止、L34 が「1 Issue ずつ完結」、L36-41 が逐次ステップ。
- implementer は `.opencode/**` の編集が権限で禁止 → 役割定義・コマンド定義の改訂は primary が行う。
- `tests/test_cli.py` TestDataSync (L347-367) が `nepoforge/data/agents/*.md` と `.opencode/agents/*.md` の一致 (model 行を除く)、`nepoforge/data/commands/nfgo.md` と `.opencode/commands/nfgo.md` の完全一致を要求。
- `docs/architecture.md` に並列実行の規定は存在しない。§3 L41「役割定義からワークフローを参照しない。委譲時の入出力契約だけを定める」。§2 図の「task 委譲」は V1 名で不整合。
- AGENTS.md L52 に「worktree や個別ブランチで分離」の既存規定あり。
- `scripts/switch_profile.py` は `model:` 行のみ差し替えるため、frontmatter の他の行の変更と干渉しない。

## 3. 決定事項

1. **委譲の集約先は primary (方式 A)**。architect に直接委譲させない (方式 B は不採用、§7)。
   - 理由: (a) experimental 設定に依存せず標準機能の既定値だけで実現できる (0002 §5 結論と一致)。(b) 権限拡大 (architect への `subagent` 許可) が不要で最小権限 (#17) を維持する。(c) 依存管理・統合・PR 作成が primary で一元化され、クリティカルパスの判断が 1 箇所に集まる。(d) before 実測のボトルネック主因は入力 226k トークンであり、これは委譲入力の要点化 (§4.1 委譲契約) で解決でき、再委譲権限は不要。
2. **権限・experimental 設定は変更しない**。5 役の permissions、`.opencode/opencode.jsonc` (guardrail)、`experimental.*` に変更を加えない。並列化は「起動の仕方 (同一ブロック) と委譲契約の質」の改訂で実現する。
3. **委譲契約を必須化し、入力は要点化する**。全委譲に目的・範囲・入出力・完了条件・依存を付す。委譲入力に調査報告等の全文を転載せず、要点と参照パスを渡す (子には read 権限があるため参照先を自分で読める)。
4. **並列化の適用範囲**: 調査は既定で並列。設計・レビューは対象が確定してからなので逐次 (ただし並列稼働中の他の子の完了処理を妨げない)。実装は条件付き並列 (編集範囲がファイル単位で分離し統合手順が明確な場合のみ)。
5. **ステップ 2 (複数 Issue は逐次) は維持**。「Issue 間の並列禁止」と「単一 Issue 内の委譲の並列許可」を明確に区別する表現に改める (L27 の表記が後者まで禁止していると読めるため)。
6. **architect の職務は「細部調査を抱え込まない技術責任者」へ明確化**。権限は変更しない。設計の粒度を「判断に足る文書」に緩和し、詳細設計書の作成を常に強制しない。

## 4. ファイル別の変更仕様

### 4.1 `.opencode/commands/nfgo.md`

変更方針: ステップ 0-2 と 4 の構造・番号は維持し、ステップ 3 をフェーズ構造に組み替える (後続ステップの番号を動かさないため)。新設する規定の骨子:

- **冒頭 (ステップ 3 の導入部)**: 「委譲の集約先は primary (このセッション) とする。子エージェントからの再委譲は行わない」を追加。
- **ステップ 3.0 タスク分解 (新設)**: primary が Issue 本文から作業項目・依存関係・完了条件を洗い出す。分解と委譲に必要な最小限の把握に留め、詳細調査は委譲する (primary の単独作業をクリティカルパスにしない)。分解結果に基づき委譲を早めに開始する。
- **ステップ 3.1 調査 (並列委譲)**: 独立した調査 (ローカル現状把握 = `explore`、公式資料 = `expert` ほか複数可) を**同一ブロックから並列起動**する。調査が 1 件しかなければ逐次でよい。現行 L36 の委譲先指定はここに吸収する。
- **ステップ 3.2 設計**: `architect` に委譲。入力は要点と参照パス (全文転載禁止)。設計子の稼働中も他の子の完了処理を妨げない。
- **ステップ 3.3 実装**: `implementer` に委譲。既定は逐次。並列起動してよいのは**編集範囲がファイル単位で分離し、統合手順 (コミット分割・確認方法) が明確な場合のみ**。編集が重なるなら逐次に切り替える (停止条件にしない)。並列実装の統合・コミット整理は primary が行う。
- **ステップ 3.4 独立レビュー**: 実装完了後、`reviewer` に委譲。レビュー対象が確定するまで開始しない。自分の実装を自分でレビューしない。
- **ステップ 3.5 修正・テスト / 3.6 PR 作成**: 現行 L40-41 の内容を踏襲。ブランチ命名・`Refs #N`・検証結果の記録等は現行どおり。
- **委譲契約 (新設小節、全委譲で必須)**: 各委譲の指示に次を含める。
  1. 目的 — なぜこの委譲が必要か
  2. 範囲 — 対象ファイル・領域、してはならないこと
  3. 入力 — 要点と参照パス (報告の全文転載はしない。Issue 本文の指示は primary が検証・要約した形で渡し、逐語転載しない — architecture.md §5 の信頼境界)
  4. 出力 — 報告に含めるべき内容 (子の最後の text 応答のみが親に届くため、text で要点を返させる)
  5. 完了条件 — 何をもって完了とするか
  6. 依存 — 他タスクとの前後関係・共有資源
- **報告の扱い (新設小節)**: 子の報告は idle ごとに届く。state=`running` は中間報告であり完了とみなさない。state=`completed` / `error` を確認して次に進む。子が `error` で終了しても、依存しない他の作業は止めない。失敗したタスクだけ再委譲・逐次実施・停止報告を判断する。並列委譲を行った場合はその旨をステップ 4 の報告に含める。
- **ステップ 2 の改訂 (L27)**: 「独立しているものも順番に処理する (**Issue 間の並列実行はしない**。単一 Issue 内の委譲の並列化はステップ 3 のとおり行ってよい)」に明確化。
- **維持するもの**: ステップ 0 (引数検証)、ステップ 1 (信頼境界)、L34「1 Issue ずつ完結」、停止条件 3 項目、禁止事項 (マージ禁止・force push 禁止・無関係変更禁止)、git・gh 操作の分担 (primary が git/gh 操作、implementer はファイル編集のみ)。

### 4.3 `AGENTS.md`

変更方針: 「開発フロー」節 (L26-36) の後に小節「委譲と並列実行 (#49)」を追加。開発フローの番号付きリスト自体は変更しない。骨子:

- 委譲の集約先は primary。子エージェントからの再委譲はしない。
- 委譲は早く行い、独立した委譲は既定で並列に起動する。逐次にするのは依存・競合など必要な場合のみ。

## 5. 安全性設計

維持するもの:

- PR マージは人間、独立レビュー、無承認マージ禁止、`gh pr merge` / force push の権限禁止 (architecture.md §6、guardrail) — 並列化で緩和しない。
- 役割の最小権限 (5 役の permissions 変更なし) と読み取り専用調査 (#17)。
- implementer による `.opencode/**` 編集禁止 → 本改訂 (役割・コマンド定義) は primary が実装する。
- 信頼境界 (architecture.md §5): 委譲契約の入力にも適用する (Issue 本文の逐語転載禁止、§4.1)。並列化で子数が増えても信頼境界の定義は変わらない。

並列化で新たに生じるリスクと緩和:

| リスク | 緩和 |
| --- | --- |
| 中間報告 (state=running) を完了と誤認 | nfgo.md 報告の扱いで state 確認を必須化 (§4.1) |
| 同時実行数の過多 (公式上限なし) | 同時に起動して待つ子はクリティカルパス上に必要なものに限る (nfgo.md・architecture.md §3) |
| 並列実装の編集競合 | ファイル単位の分離条件 + 重複時は逐次へ切替。統合・コミットは primary が逐次で実施 |
| 報告が text のみで構造化されない | 委譲契約の出力項目で報告形式を指定 |
| 一部の子の失敗による全体停止 | 失敗時も依存しない作業を継続する規定 (§4.1) |

## 7. 代替案と不採用理由
